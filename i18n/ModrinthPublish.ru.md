# XMCL Modrinth Publish

## Предыстория

XMCL уже поддерживает просмотр, установку и экспорт модпаков Modrinth, а также получил через OAuth разрешения на чтение, создание и изменение проектов/версий Modrinth. Текущий процесс публикации по-прежнему требует, чтобы пользователь покидал лаунчер, экспортировал файлы локально, а затем вручную создавал проект или версию на сайте Modrinth и загружал их.

Экземпляр XMCL также может работать как локальный выделенный сервер (dedicated server). Публикация в Modrinth должна использовать возможности декларации окружения MRPack для описания клиентских и серверных файлов, вместо создания дополнительного ZIP-архива для готового к запуску сервера.

## Цели продукта

Предоставить авторам модпаков возможность выполнять полный цикл публикации в Modrinth прямо из XMCL:

1. Собрать из текущего экземпляра MRPack, соответствующий спецификации Modrinth: универсальный (universal), только для клиента (client-only) или только для сервера (server-only).
2. Создать новый проект модпака на Modrinth или выбрать существующий проект, которым текущая учётная запись имеет право управлять.
3. Создать версию для проекта, заполнить необходимые метаданные для публикации и загрузить собранные артефакты.
4. Для экземпляров с настроенным локальным выделенным сервером по умолчанию генерировать и публиковать версию с универсальным MRPack в качестве основного файла.
5. Сохранять связь между экземпляром и проектом Modrinth, чтобы при последующих выпусках не приходилось заново выбирать проект и заполнять неизменяемую информацию.
6. Перед загрузкой наглядно показывать метаданные и файлы, которые станут публичными; в случае сбоя выдавать понятный результат с возможностью повтора без случайного дублирования публикации.

Под "единым процессом" здесь понимается, что пользователю не нужно вручную открывать сайт Modrinth или повторно загружать локально экспортированные файлы. Проверка модпаков, соответствие требованиям и финальная страница проекта остаются на усмотрение платформы Modrinth.

## Черновик пользовательского сценария

### Первая публикация

1. Пользователь выбирает "Опубликовать в Modrinth" в разделе модпаков/экспорта экземпляра.
2. XMCL проверяет статус входа, разрешения OAuth, состояние выполнения экземпляра и файлы, готовые к публикации.
3. Пользователь выбирает:
   - Создать новый проект; или
   - Опубликовать в существующий проект, которым он имеет право управлять.
4. Пользователь заполняет или подтверждает информацию о проекте и версии.
5. XMCL предварительно выбирает профиль MRPack на основе состояния экземпляра; пользователь может оставить значение по умолчанию или выбрать раздельный вывод client-only и server-only MRPack, а также проверить файлы в каждом профиле.
6. XMCL сначала собирает и локально проверяет артефакты, затем создаёт/обновляет удалённый черновик и загружает файлы.
7. Пользователь проверяет черновик и явно отправляет его на публикацию/проверку; XMCL не публикует новый проект/версию по умолчанию сразу.
8. После успешной публикации XMCL сохраняет связь экземпляра с проектом и предоставляет ссылку для открытия страницы проекта/версии на Modrinth.

### Последующие выпуски

1. XMCL автоматически выбирает проект на основе сохранённой связи с экземпляром и получает актуальное состояние с сервера.
2. Пользователь заполняет новые поля версии: номер версии, заголовок, список изменений, канал релиза и т.д.
3. XMCL заново собирает выбранные артефакты, показывает изменения по сравнению с предыдущим выпуском и создаёт новую версию.

### Управление проектами

- Предоставить отдельную страницу управления Modrinth, где отображаются связанные с экземпляром проекты, история удалённых версий, статус черновиков и результаты последних публикаций.
- Пользователь может изменять метаданные проекта/версии на странице управления, а также начинать новый выпуск оттуда.
- Мастер публикации сосредоточен на текущей сборке, полях версии и подтверждении загрузки, а не на полноценном администрировании Modrinth.

## Объекты публикации

### Профили MRPack

- Использовать существующую возможность сборки `.mrpack` для Modrinth и расширить её до трёх выходных профилей:
  - `universal`: один манифест, описывающий файлы, необходимые как для клиента, так и для сервера.
  - `client-only`: содержит только файлы, необходимые для установки клиента, и overrides.
  - `server-only`: содержит только файлы, необходимые для установки выделенного сервера, и overrides.
- Универсальный MRPack использует в манифесте для каждого файла поля `env.client` / `env.server`, чтобы указать потребности обеих сторон, а также использует `overrides/`, `client-overrides/` и `server-overrides/`.
- Universal и server-only MRPack - это структурированные установочные пакеты, совместимые с установщиками MRPack, но не гарантирующие, что сервер запустится сразу после распаковки.
- В первой версии не генерировать и не загружать готовый к запуску серверный ZIP-архив.

### Выбор по умолчанию и основной файл

- Если у экземпляра не настроен локальный выделенный сервер, по умолчанию собирается только client-only MRPack, который становится основным файлом версии Modrinth.
- Если у экземпляра настроен локальный выделенный сервер, по умолчанию собирается только universal MRPack, который становится основным файлом.
- Для экземпляров с настроенным локальным сервером пользователь может включить "раздельный вывод". При этом для одной версии Modrinth загружаются universal, client-only и server-only MRPack, а universal остаётся основным файлом.
- Все три профиля используют один и тот же проект, номер версии, канал релиза, версии игры, загрузчики и список изменений; отдельная версия или проект для server-only не создаётся.
- Файлы получают стабильные имена: `<project>-<version>.mrpack`, `<project>-client-<version>.mrpack` и `<project>-server-<version>.mrpack`.
- При включённом "раздельном выводе" XMCL автоматически добавляет в список изменений версии пояснение о назначении трёх файлов, чтобы пользователям не приходилось полагаться только на список файлов и имена для определения цели установки.

### Ограничения API Modrinth

- Использовать `POST /version` с multipart-запросом для одновременного создания версии и загрузки всех выбранных MRPack.
- В запросе поле `file_parts` перечисляет имена multipart-частей для каждого загружаемого файла; `primary_file` указывает на часть, соответствующую универсальному MRPack. Для обычного экземпляра, где выводится только client-only, `primary_file` указывает на client-only MRPack.
- API Modrinth принимает `.mrpack` и позволяет указать несколько `file_parts` в одном запросе версии; документация API не ограничивает одну версию одним `.mrpack`.
- Черновик версии можно создать без файлов; обычный процесс публикации XMCL всё равно загружает все выбранные файлы в первом запросе, чтобы не полагаться на последующие добавления.
- `PATCH /version/{id}` предоставляет поля `status` и `requested_status`; XMCL использует этот интерфейс для отправки или изменения статуса публикации после проверки черновика.
- Для создания, чтения и изменения проектов/версий используются соответствующие разрешения OAuth-приложения XMCL Modrinth.

### Классификация файлов и безопасность

- Зависимости следует сначала включать в манифест Modrinth; если зависимость нельзя получить по разрешённому URL-адресу загрузки, она либо добавляется как override по выбору пользователя, либо блокирует публикацию.
- Загрузчик, версия Minecraft и информация о клиентском/серверном окружении должны определяться из экземпляра, а пользователь должен иметь возможность проверить их перед публикацией.
- При сборке серверного окружения использовать существующие правила выбора файлов для выделенного сервера, чтобы избежать включения логов, кэша, учётных данных, ключей или других локальных приватных данных в MRPack.
- Серверный профиль по умолчанию включает `server.properties`; мир, данные игроков, списки ops/whitelist/ban и параметры запуска исключаются по умолчанию и должны быть явно выбраны пользователем.
- Для `eula.txt`, мира, данных игроков, вайтлистов, бан-листов, адресов серверов и учётных данных должны быть чёткие политики; они не могут автоматически включаться ни в один профиль.

## Проверяемые цели (Definition of Done)

### Учётная запись и разрешения

- Если пользователь не вошёл в Modrinth, точка входа в публикацию предлагает пройти OAuth-вход; отмена входа не приводит к потере заполненного черновика публикации.
- При недостаточных правах, истёкшем токене или отсутствии прав на управление целевым проектом выдаётся чёткое сообщение до создания удалённых объектов и предлагается повторная авторизация.
- Можно выбирать только те проекты, на создание версий/изменение которых у текущей учётной записи есть права; публикация по ID проекта без прав невозможна.

### Создание нового проекта

- Пользователь может заполнить в XMCL все обязательные и часто используемые необязательные поля для создания проекта модпака на Modrinth и увидеть ошибки проверки платформы, привязанные к конкретным полям.
- Форма первой версии как минимум покрывает: название, slug, краткое описание, полное описание, лицензию, категории, поддержку клиента/сервера и иконку; для редких расширенных настроек можно предоставить ссылку на сайт Modrinth для продолжения редактирования.
- После успешного создания проект появляется на сайте Modrinth, а его название, slug, краткое описание, полное описание, лицензия, категории, поддерживаемые версии игры/загрузчики, статус поддержки клиента/сервера и иконка соответствуют тому, что подтвердил пользователь.
- Если проект создан, но загрузка версии не удалась, XMCL явно показывает состояние "частичного успеха" и позволяет продолжить работу с этим проектом, не создавая повторно дублирующийся проект.
- Первая версия также поддерживает изменение публичных метаданных существующего проекта; все изменения должны показываться в виде различий и подтверждаться пользователем перед отправкой.
- Связь с проектом, выбор файлов и значения по умолчанию для публикации сохраняются в метаданных экземпляра и участвуют в синхронизации экземпляров; OAuth-токены и любые учётные данные не попадают в метаданные экземпляра или синхронизируемые данные.
- При возникновении конфликта синхронизации конфигурации публикации между двумя устройствами для одного экземпляра перед публикацией отображаются локальная и синхронизированная версии, и пользователь выбирает, какую использовать; автоматическая перезапись по времени последнего изменения не допускается.

### Публикация новой версии

- Пользователь может создать версию для уже связанного или вручную выбранного проекта, указав как минимум: номер версии, заголовок, список изменений, канал релиза, версию игры и загрузчик.
- Перед загрузкой XMCL проверяет конфликты номера версии/имени файла, обязательные поля, пустые артефакты, размер файлов и ограничения API Modrinth, которые можно проверить заранее.
- После успешной публикации метаданные и файлы на странице версии Modrinth соответствуют тому, что пользователь подтвердил перед отправкой; основной файл указан верно, а хеши файлов можно сверить с локальными артефактами.
- Сбой сети или ошибка API не отображаются как успех; перед повторной попыткой выполняется проверка удалённого результата, чтобы избежать создания дублирующей версии.
- Первая версия поддерживает изменение метаданных версии, но не предоставляет архивацию, снятие с публикации (unlist) или безвозвратное удаление проекта/версии.
- Для черновика версии можно заменять файлы; после того как версия становится публичной, артефакты считаются неизменяемыми, и любые изменения файлов требуют создания новой версии с новым номером.
- Новые проекты/версии по умолчанию сохраняются как черновики. Только после того, как пользователь явно выполнит действие по отправке после завершения загрузки и проверки результата, версия переходит в статус публичной или ожидания проверки платформы.

### Профили MRPack

- После публикации client-only MRPack из обычного экземпляра этот пакет можно установить через Modrinth как новый клиентский экземпляр и успешно запустить.
- После публикации universal MRPack из экземпляра с настроенным локальным сервером этот же файл можно установить как клиентский экземпляр и как выделенный сервер, и в обоих случаях он успешно запустится в соответствующем окружении.
- При включённом "раздельном выводе" наборы файлов в client-only и server-only MRPack должны совпадать с результатами разбора universal MRPack по признаку client/server окружения.
- В универсальном манифесте корректно указаны Minecraft, загрузчик, зависимости, `env` и пути override; клиентские файлы не попадают в серверную установку, а серверные - в клиентскую.
- Universal является основным файлом; client-only и server-only файлы при раздельном выводе доступны для загрузки в той же версии Modrinth, и все три файла имеют одинаковые метаданные версии.
- При раздельном выводе список изменений версии Modrinth содержит дополнение от XMCL с пояснением назначения файлов, сохраняя при этом исходный список изменений пользователя.
- Ни один профиль не включает токены учётных записей, SSH-ключи, логи, отчёты об ошибках, кэш или невыбранные явно данные мира/игроков.
- При обнаружении зависимостей, которые нельзя легально распространять или которые не соответствуют правилам доменов загрузки Modrinth, перед публикацией выводится список проблем и способы их решения, а не просто пропуск.

### Состояние, восстановление и наблюдаемость

- Процесс публикации разделён на этапы: сборка, проверка, создание проекта, создание версии, загрузка файлов и завершение; для каждого этапа отображается причина сбоя и возможные действия.
- После закрытия или обновления страницы уже выполненные удалённые шаги можно определить; черновик публикации сохраняет удалённые ID проекта/версии и результаты этапов, позволяя пользователю продолжить с незавершённого этапа или отказаться от черновика.
- В первой версии не требуется дозагрузка отдельных файлов с поддержкой возобновления; при прерывании загрузки файла его можно перезагрузить, но нельзя создать повторно проект/версию.
- Страница успеха содержит ссылки на проект/версию, а также сохраняет ID проекта, ID версии, хеш артефактов и время последней публикации.
- Все собранные MRPack сохраняются локально; в первой версии для сквозного приёмочного тестирования используется ручная установка и запуск тестировщиками с клиентской и серверной целью, автоматические дымовые тесты не требуются.
- Артефакты по умолчанию сохраняются в каталоге, структурированном по проекту/версии Modrinth; имена файлов в этом каталоге соответствуют именам загруженных файлов для поддержки повторных попыток, аудита и сверки хешей.
- Локальные артефакты хранятся 30 дней с момента сборки; задача очистки удаляет только те артефакты, которые старше 30 дней и не относятся к активным черновикам публикации. Удаление локальных артефактов не влияет на записи о публикациях и удалённые проекты/версии.

## Что не входит в первую версию

- Замена в XMCL систем проверки модпаков, модерации, управления командой и доходами платформы Modrinth.
- Автоматический обход лицензионных ограничений сторонних файлов или ограничений платформы Modrinth.
- Автоматическая публикация на CurseForge или других платформах.
- Автоматическое перезапись метаданных проекта, удаление удалённых версий или публикация новых версий без явного подтверждения пользователя.
- Архивация, снятие с публикации (unlist) или безвозвратное удаление удалённых проектов/версий.
- В первой версии - полная поддержка CI/CD, публикации по расписанию или совместного редактирования одного черновика несколькими пользователями.
- Дозагрузка отдельных файлов по частям с поддержкой возобновления.
